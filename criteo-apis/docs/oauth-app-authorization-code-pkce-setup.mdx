## PKCE Overview

Proof Key for Code Exchange (PKCE) is an extension of the OAuth 2.0 Authorization Code flow that enhances security for public or mobile clients that cannot safely store a client secret. It adds a verification step between the authorization request and token exchange to prevent intercepted authorization codes from being reused by malicious actors.

You should use PKCE if your application is a mobile app, single-page app (SPA), or any client that cannot securely store a client secret. If your application is a traditional server-side (confidential) client, you can continue using the standard [Authorization Code flow](/criteo-apis/docs/oauth-app-authorization-code).

<Info>
  PKCE (RFC 7636) is also available to developers as an extension of the authorization code flow. To enable it, toggle `PKCE` in the App details page.

  Once PKCE is enabled, the application can only use the PKCE workflow. If PKCE parameters are not provided, the authorization code flow will fail. To switch back the toggle, the application should have no active keys.
</Warning>

## Step 1. Consent URL

Once your app parameters are set, you can implement the authorization code flow.

### Consent URL

To request access, create a Consent link that redirects the user.

<Info>
  #### Authorization Code vs. Client Credentials Consent URLs

  If you're familiar with the [Client Credentials workflow](/criteo-apis/docs/oauth-app-client-credentials), you might notice that the **Generate Consent URL** button is not present in the partner portal for the authorization code workflow. This is because, with the authorization code method, you need to provide a redirect URI specific to your organization. Therefore, these URLs must be configured directly within your workflow.
</Info>

<Warning>
  If the redirect URI is not declared in the application, the redirection will be blocked.
</Warning>

If you have PKCE enabled, then the consent URL will require additional parameters:

```http URL
https://consent.criteo.com/request?response_type=code
&client_id={client_id}
&redirect_uri={redirect_uri}
&state={state}
&code_challenge={code_challenge}
&code_challenge_method={code_challenge_method}
```

## Step 2. Exchanging the Authorization Code for an Access Token

<Info>
  You can find more details about the OAuth endpoint in [our API Reference](/retail-media/reference/authorization/get-token).
</Info>

If you have PKCE enabled, your token request must include `code_verifier`. The `client_secret` is optional — the `code_verifier` authenticates the request in its place. If you do send a `client_secret`, it must be valid.

### Example Request

```bash
curl -L 'https://api.criteo.com/oauth2/token' \
-H 'Content-Type: application/x-www-form-urlencoded' \
-d 'client_id=<MY_CLIENT_ID>' \
-d 'redirect_uri=<MY_URI>' \
-d 'code=<MY_CODE>' \
-d 'grant_type=authorization_code' \
-d 'code_verifier=<MY_CODE_VERIFIER>'
```

### Example Response (Success)

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_in": 900
}
```

## Step 3. Using the Refresh Token

PKCE refresh tokens are short-lived and the session has a hard cap. The table below summarizes the differences from a standard app.

| | Standard app | PKCE app |
| --- | --- | --- |
| `client_secret` on refresh | Required | Optional (validated if provided) |
| Refresh token lifetime | 180 days | 3 hours |
| Maximum session length | None | 24 hours from the initial code exchange |
| `client_id` must match the token's client | Not enforced | Enforced (`invalid_grant` if mismatched) |
| Tokens issued on refresh | Standard | Still PKCE; the 24-hour start time carries over |

**How the 24-hour cap works:** each refresh returns a new refresh token, but the session start time is carried over and never resets. Each new refresh token's lifetime is the smaller of 3 hours and the time remaining in the 24-hour session. Once the 24-hour limit is reached, the refresh fails with `invalid_grant` and the user must re-authorize through the full authorization code and PKCE flow. Always store the latest refresh token — previous ones are invalidated on each refresh.

### Example Request

```bash
curl -X POST https://api.criteo.com/oauth2/token \
-H "Content-Type: application/x-www-form-urlencoded" \
-d "grant_type=refresh_token" \
-d "refresh_token={refresh_token}" \
-d "client_id={client_id}"
```

## Error Codes

| Code | HTTP status | When it occurs |
| --- | --- | --- |
| `invalid_client` | `400` | Wrong `client_secret`, or `client_secret` is missing for a non-PKCE app. |
| `invalid_grant` | `400` | Expired, invalid, or already-used refresh token; `client_id` mismatch on a PKCE refresh; or a PKCE session past its 24-hour limit. |
| `invalid_request` | `400` | Missing `client_id`. |
